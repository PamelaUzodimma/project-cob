# COB — Internal Infrastructure Provisioning Platform

## What is COB?

COB is Beejan Technologies' internal Terraform platform for provisioning
standardised AWS infrastructure. It exists so engineering teams can move
from *"we need AWS infrastructure, can Platform Engineering build it for
us?"* to *"we can provision what we need using the company's standard
platform."*

## The problem COB solves

Before COB, every team requesting infrastructure got a hand-built,
one-off set of AWS resources. This produced real, growing inconsistency:
some S3 buckets had versioning enabled, others didn't; IAM policies
varied team to team; naming and tagging weren't standardised; and every
request funnelled through Platform Engineering as a manual bottleneck.

COB replaces that with reusable Terraform modules that encode secure,
consistent defaults once, centrally -- so every team gets the same
baseline without re-implementing it, and Platform Engineering can improve
the standard in one place instead of N places.

## What COB provides

Six platform capabilities, each a real abstraction (not a thin wrapper
around a single AWS resource):

| Capability | Module | What it gives a team |
|---|---|---|
| Networking | `modules/networking` | VPC, public/private subnets across AZs, routing, baseline security group |
| Identity & Access | `modules/iam` | Least-privilege IAM roles built from scoped action/resource statements |
| Object Storage | `modules/storage` | Encrypted, versioned, TLS-enforced S3 buckets with lifecycle management |
| Compute | `modules/compute-ecs` | Fargate ECS service with execution role, logging, and scoped security group |
| Relational Database | `modules/database-rds` | RDS instance with auto-generated Secrets-Manager-stored credentials |
| Data Platform | `modules/data-platform` | Glue Catalog + Crawler + Athena workgroup for querying S3 data |

See `docs/modules/` for detailed documentation of each.

## Repository structure

```
cob/
├── modules/          # the platform itself -- reusable capabilities
├── environments/     # environment-specific composition (dev, prod)
├── examples/         # standalone reference consumer
├── bootstrap/        # one-time Terraform state backend setup
└── docs/             # module docs, architecture, decision records
```

`modules/` contains no environment-specific values. `environments/`
contains no reusable logic -- only module calls with environment-
appropriate variable values. This separation is what makes the platform
reusable across environments without duplicating code.

## Supported environments

- **dev** -- applied and live; NAT disabled (cost), single-AZ RDS, small instance sizes
- **prod** -- fully configured and `plan`-validated; NAT enabled, Multi-AZ RDS, larger instance sizes, longer retention. Intentionally not applied as part of this submission -- see `docs/decisions/0003-prod-not-applied.md`.

## How to consume COB

See `examples/web-app-with-datastore/` for a complete, standalone
reference showing how a team composes all six capabilities together.

Each module in `modules/` has its own README in `docs/modules/`
documenting required inputs, outputs, and security considerations.

## Security considerations

- All S3 buckets: encrypted at rest, versioned, public access blocked, TLS-only bucket policy
- All IAM roles: built from explicit action+resource statement lists -- no wildcard access by default
- RDS: no plaintext passwords anywhere in configuration; passwords are generated by Terraform and stored in AWS Secrets Manager
- All compute and database resources run in private subnets; nothing is reachable from the public internet by default
- Security group access between services (e.g. compute -> database) is granted via security-group-to-security-group rules, not CIDR ranges, wherever practical

## Known limitations

- `dynamodb_table` for state locking uses the (functioning but deprecated) legacy Terraform S3 backend locking mechanism; a future iteration should migrate to native S3 locking (`use_lockfile`)
- EC2 compute (as opposed to ECS/Fargate) is documented as a planned capability but not implemented in this version -- ECS/Fargate was prioritised as it demonstrates the same abstraction patterns
- The `compute-ecs` module does not provision a load balancer; a service is reachable only within the VPC. Adding an ALB module is a natural next iteration.
- `prod` is configuration-validated (`terraform plan` succeeds) but not applied, by deliberate scope decision given project timeline -- see ADR 0003.

## Major architectural decisions

See `docs/decisions/` for full reasoning. Summary:
- **0001** -- Module boundaries drawn around capabilities, not individual AWS resources
- **0002** -- Consistent tagging/naming strategy applied via shared `locals` pattern in every module
- **0003** -- Prod environment built and validated but not applied, given assignment timeline
- **0004** -- RDS credentials generated by Terraform and stored in Secrets Manager, never passed as plaintext variables
